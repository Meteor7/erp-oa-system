## 0. 已定决定（评审后，覆盖下面的初稿）

- **不做月结**（月结进度、期间锁定、月结清单都不做）。
- **不再屏蔽任何账号**：副总可以看社保、公积金、工资汇总；总经理可以打开物料进度看板。屏蔽的机制保留（`HR_SENSITIVE_HIDDEN_USERS` 现在是空集）。
- **系统里没有「逾期」口径，用「等待时长」代替**：待付款 = 报销单 / 付款单「待办理」（只差出纳付款）+ 采购付款期次「待实际付款」；「等待超过 3 天」= 从最近一次审批通过算起超过 3 天（不含）。采购付款填了计划付款日且已过的，另算「已过计划付款日」；没填计划日的不算。
- **审批卡点统一「超过 3 天」**，从最近一次签批起算（没有就从提交），范围：报销、付款、采购申请、购买申请、出差、采购付款、价格审批；不含请假、加班、调休。
- 工资条「待复核」= 草稿；不显示发薪日。社保「待确认」= 导入批次里待确认的行。公积金「有差异」不做。
- 付款类型用系统现有的 `payment_stage`（预付款 / 到货款 / 尾款 / 到货后全额付款）；不做准时到货率、验收一次通过率；我的报销不显示预计到账日。
- 发票块用系统现有状态名（待确认、疑似重复、识别失败…），不叫「待核对」。
- **PMC 的所有块不出现任何金额**；生产主管只看到货验收类。
- **多身份取并集**：首页按最高优先级身份排版；每个块的 `visible` 看真实权限（不看 profile），所以人事经理同时是部门主管也不丢权限。
- 「研发 N」= 研发类型是全时 / 非全时 / 辅助的在职人数；「填工时 M」= 工时填报名单人数（排除免填账号）。
- 财务主管不看人力成本汇总，总账会计不看社保公积金缴纳总额（与现有页面权限一致）。
- 物料「合同交期已过」：接口给每行 `contract_overdue`（PO 合同已生效、合同交期已过、还没收齐），看板和物料进度页同一口径；没填合同交期的不算。
- 看板首页不再有「我的假期」「我发起的申请」两块（由指标卡和块覆盖）；「通知」区块保留在总览最下面。

## 1. 目标

现在的数据看板有四个页签（我的待办 / 经营看板 / 人事看板 / 研发核算），老板要点三次才拼得出公司整体，经营看板只讲费用，没有"钱要流出多少、卡在哪"，人事看板只讲请假，研发核算讲流程完成度。后来加的东西（付款与采购链路、工时填报进度、宿舍、薪酬、社保公积金、月结、研发类型缺口）都没有进看板。

目标：每个岗位打开看板，第一屏就是**它该处理的事**和**它该关心的数**，点任何一个数字或提醒，直接带着筛选打开对应页面。

原则：

1. **总览 = 待办 + 关注 + 指标卡，同一屏。** 经营、人事、研发、薪酬与社保、宿舍等是往下钻的页签，只给需要的岗位。
2. **权限由服务端决定。** 看板接口按调用者的岗位、角色、屏蔽状态，只返回他能看的块；前端不写死岗位。
3. **敏感信息只给汇总。** 薪酬、社保、公积金只显示人数、进度、汇总金额，不出现个人的数；被屏蔽的账号整块不返回。
4. **每个数字都来自现有数据。** 已有接口复用，没有的才新写聚合函数；不写没有数据来源的卡片。
5. **前后端用同一套"目标名"对齐跳转**，用测试卡住（见 §5）。

## 3. 接口约定（草案）

`rayher_hr_payroll.api.dashboard_home.get_dashboard_home(period=None)`，GET，登录即可调用。服务端判断岗位和权限，返回：

```json
{
  "role": {"key": "vice_manager", "label": "副总经理", "person": "演示员工21", "note": "…"},
  "period": "2026-10",
  "tabs": [{"key": "overview", "label": "总览"}, {"key": "cost", "label": "经营"}],
  "pages": {
    "overview": {
      "kpis":   [{"key": "pay.unpaid", "label": "待付款", "value": "128.6", "unit": "万", "sub": "共 18 笔 · 逾期 3 笔", "tone": "bad", "target": {"key": "payment.unpaid", "params": {}}}],
      "alerts": [{"key": "pay.overdue", "tone": "bad", "title": "…", "sub": "…", "go": "付款申请", "target": {"key": "payment.overdue"}}],
      "todos":  [{"kind": "付款单", "title": "…", "sub": "…", "btn": "去审批", "target": {"key": "payment.detail", "params": {"request": "OA-…"}}}],
      "blocks": [{"type": "bars|cols|stack|list", "title": "…", "sub": "…", "rows": [], "target": {"key": "…"}, "error": null}]
    }
  }
}
```

约定：

- **每个块独立计算、独立失败**：某个块出错，只在该块的 `error` 里写原因，其余照常返回。
- **没权限的块不返回**，不是返回空或灰掉。
- **数字带口径**：每个 kpi / block 可带 `hint`（口径一句话），前端放在小问号里；预览数字带 `preview: true`。
- **缓存**：按用户 + 期间缓存 60 秒；待办不缓存（沿用现有 `get_my_approval_queue`）。
- 已有接口原样保留：`get_my_approval_queue`、`get_my_requests`、`get_my_leave_summary`、`get_cost_overview`、`get_hr_overview`、`get_dashboard`。新接口在内部复用它们的计算，不重复写口径。

## 5. 怎么保证前后端对得上

1. **后端测试**：`DASHBOARD_TARGETS`（目标名 → 允许的参数名）是唯一来源；测试检查接口返回的每个 `target.key` 都在里面，参数名都在允许范围内。
2. **前端测试**：`dashboardTargets.js` 里每个目标都对应 `router.js` 里存在的路由，`canSee` 的角色与后端该目标的可见岗位一致，目标页确实读取这些查询参数（读源码断言，沿用 `nav-source.test.js` 的做法）。
3. **共享固定件**：后端从 `DASHBOARD_TARGETS` 生成 `frontend/tests/fixtures/dashboard-targets.json`，前端测试读它；后端测试断言文件与生成结果一致，改了一边不改另一边就失败。
4. **每个岗位一个后端测试**：用假数据调用接口，断言该岗位只拿到对照表里允许的块（例如人事经理没有任何付款相关块，副总没有任何社保 / 公积金 / 工资块）。
5. **验收站**：用不同岗位的账号逐个打开首页，点每张卡、每条提醒，确认落在对的页面且筛选生效。

## 6. 目标页需要补的"从地址读筛选"

原型里很多跳转，目标页现在的筛选只是页面内部状态，不在地址里。这些页面要补（具体清单以核对结果为准）：员工信息、工时填报（填报进度视图）、薪酬、社保、公积金、宿舍的三个页面、采购付款、物料进度、发票夹，以及考勤中心的 `/approval/attendance` 路由。沿用 #72 的做法：筛选进地址，详情页返回时回到原来的筛选。
