# OA 审批审查缺陷修复设计

日期：2026-08-17

## 目标

修复已确认的审批闭环、数据完整性、看板金额、请假可用性和写接口安全问题，不扩展金蝶、供应商合并付款或人工异常审批的挂起范围。

## 设计

### 采购履约与尾款

采购申请作为同一采购需求的履约汇总记录。已付款的预付款或全额付款单仍是到货、验收、核销操作入口；每次有效履约变更同时同步到其来源采购申请。新建后续到货款或尾款时，从来源采购申请复制累计到货、验收和异常状态，因此提交校验能读取上一阶段的真实履约结果。

付款单继续保存自己的审批、付款和证据快照。尾款必须重新上传或关联有效验收资料，不能只依赖历史文件名。

### 审批数据完整性

除服务端字段外，主题、供应商、付款阶段、预付款比例、尾款标志、交期、项目、资产分类、经办人和业务明细等决定审批结论的字段，仅允许在草稿状态修改。驳回申请人会把单据变回草稿并重置全部审批节点；驳回上游节点但不退申请人时，不允许修改业务内容。

### 付款看板

采购付款行按付款单自己的金额流水计算：
- 申请金额：付款单金额；
- 批准金额：付款已完成时为付款单金额；
- 占用金额：该付款单尚未释放的占用；
- 已付金额：该付款单已付款流水；
- 可用余额：付款单金额减占用和已付，不重复统计来源采购申请余额。

来源采购申请剩余可用金额继续在申请看板展示。

### 请假

将 Docker 站点的请假功能从演示员工170限定改为普通员工可访问。申请人、部门、直属主管仍完全从当前登录账号关联的在职员工读取，演示员工170没有员工关系时仍不得演示员工106员工请假。

### 接口与加载状态

所有写入草稿、归档资料和履约变更接口强制 POST。申请、付款看板在异步数据返回前显示加载状态，不先显示错误的零值空看板。采购表单在提交前显示当前账号组织信息缺失的明确提示。

## 数据处理

删除确认属于误操作且仍为无步骤草稿的 OA-2026-00187。现有正式测试批次保留，用于修复后回归。已有付款履约数据通过一次性定向回填把到货、验收状态同步到来源采购申请。

## 验证

必须覆盖：
1. 预付款付款后登记到货验收，新尾款草稿继承状态并可提交；
2. 审批中修改供应商或付款阶段被拒绝；
3. 付款看板得到占用 50、已付 150；
4. 普通员工可以访问请假，未关联员工仍不能提交；
5. 写接口只允许 POST；
6. 后端相关测试、前端全量测试、生产构建和 Docker 数据核对全部通过。
