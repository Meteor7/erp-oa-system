# 临时报销功能总开关设计

## 目标

在研发人员参与系统测试期间，临时关闭费用付款/报销功能。关闭状态下仅当前管理账号 `Administrator` 可以查看和操作报销；其他所有账号均不可见、不可访问、不可调用相关接口。现有报销数据和审批记录保持不变，后续可以通过一个站点配置开关恢复原有权限。

## 范围

本设计仅控制“费用付款/报销”及其附属能力，包括：

- 费用付款/报销菜单、页面和直接路由；
- 发票上传、OCR、确认、预览和下推；
- 报销草稿、提交、审批、驳回、加签和付款确认；
- 报销统计和审批记录；
- 报销附件访问。

请假审批、研发工时、研发台账、人事信息、宿舍费用、项目管理及其他模块的现有权限不变。本设计不删除或修改任何已有报销单、发票、审批步骤、操作日志和附件。

## 方案选择

采用站点级功能开关，不修改用户角色，也不把临时限制永久写死在现有角色矩阵中。

站点配置项：

```json
{
  "expense_reimbursement_admin_only": 1
}
```

规则如下：

1. 配置为 `1` 时，仅精确用户 `Administrator` 可以使用报销功能。
2. 配置为 `0` 或未配置时，恢复当前既有的角色、申请人和审批人权限规则。
3. `Administrator` 在关闭状态下仍可完整测试报销流程。
4. 开关只改变访问能力，不改变任何业务数据或审批状态。

选择站点开关而不是删除角色或硬编码屏蔽，原因是恢复操作可控、无需数据迁移，并且不会破坏已经配置好的审批账号和权限。

## 权限执行

### 前端

后端在页面启动信息中返回当前用户是否可访问报销功能。前端使用该服务器判定结果：

- 不渲染“费用付款/报销”菜单；
- 不把报销页作为默认落地页；
- 直接访问 `/approval/purchase` 时显示 403；
- 不预加载报销页面的数据或资源。

前端隐藏只是体验层控制，不作为安全边界。

### 后端

增加一个集中式策略函数，统一判断：

- 开关是否启用；
- 当前会话用户是否为 `Administrator`；
- 开关关闭时是否满足原有报销权限。

所有报销相关的白名单接口在入口处调用该策略。共享接口必须按请求类型处理：请假请求继续正常工作；显式请求费用付款/报销时返回权限错误；混合列表对无权用户过滤掉报销记录。

发票 OCR、报销附件、报销统计和审批动作必须使用同一策略，避免用户通过手工请求或旧页面链接绕过前端限制。

## 关闭期间的行为

- 非 `Administrator` 用户看不到报销菜单。
- 非 `Administrator` 用户手工输入报销地址会看到 403。
- 非 `Administrator` 用户调用报销接口会收到权限错误，不返回报销数据。
- 现有待审批报销单保持原状态，不自动撤回、不推进，也不删除。
- 报销相关的历史数据继续保存在数据库中。
- 其他模块和请假审批继续按原权限工作。

## 恢复方式

将站点配置 `expense_reimbursement_admin_only` 改为 `0` 或删除该配置，然后清理站点缓存。恢复后立即重新使用原有权限矩阵，无需：

- 重建账号；
- 重新关联 Employee；
- 重建审批流程；
- 修改已有报销单；
- 执行数据库迁移。

## 测试与验收

自动化测试至少覆盖：

1. 开关启用时 `Administrator` 可以访问报销页面和接口。
2. 开关启用时员工、部门主管、财务、人事、演示员工37和演示员工28均无法访问。
3. 非管理员手工访问路由显示 403，菜单不显示。
4. 非管理员无法通过报销、OCR、附件、统计或审批接口绕过限制。
5. 请假审批和研发工时不受影响。
6. 开关关闭后恢复现有角色和申请人/审批人权限。
7. 切换开关前后报销数据数量和审批状态不发生变化。

部署到当前 Docker 站点后，使用 `Administrator` 和至少一个普通研发测试账号分别验证允许与拒绝路径，并确认主机代码、Docker 代码和远程分支一致。

## 非目标

本次不重新设计报销审批流，不修改人员组织架构，不删除测试或正式数据，也不实现看板提醒功能。角色化数据看板仍作为后续独立设计继续推进。
