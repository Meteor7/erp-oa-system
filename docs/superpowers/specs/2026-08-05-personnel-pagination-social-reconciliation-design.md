# 员工信息分页与社保独立复算设计

日期：2026-08-05
范围：仅本地 Docker 开发环境

## 目标

1. 改善员工信息表的可读性：固定表头和第一列，固定每页 20 人，保留所属公司和部门筛选。
2. 在员工新增、编辑和列表中完整维护并展示社保核对所需的基础资料，包括社保基数、公积金基数和户口信息。
3. 将社保对账改为独立复算：后台使用员工档案数据和对应期间政策计算应缴金额，再与上传 Excel 逐项比较。
4. 完成社保批次的待确认、备注确认、忽略、整批确认和整批取消流程，同时保留正式明细和历史审计。

## 已确认的业务口径

### 员工信息

- 员工表固定第一行表头和最左侧第一列。
- 固定每页 20 人，不提供每页数量切换。
- 翻页后保留所属公司、部门和关键词筛选。
- 列表优先展示：序号、员工号、所属单位、姓名、部门、职位、户口信息、系统户籍判断、社保基数、公积金基数、入职日期、状态；其余既有字段继续保留横向查看。
- 新增和编辑员工时，户口信息使用下拉选项：
  - 深圳
  - 广东省内城镇
  - 广东省内农村
  - 广东省外城镇
  - 广东省外农村
- 系统判断：深圳为深户；其他四项为非深户；空值或历史异常值为待完善。
- 户口信息、社保基数或公积金基数缺失时，在列表中明确显示“未维护”，不能以空白代替。

### 社保独立复算

后台计算输入必须来自员工档案，而不是 Excel：

- 员工身份：身份证优先，姓名唯一匹配作为辅助。
- 所属公司：员工档案所属公司。
- 社保基数：员工档案社保基数。
- 深户/非深户：员工档案户口信息映射。
- 政策参数：按社保期间和所属公司选择对应政策。

Excel仅作为申报结果来源，读取缴费工资、各险种金额、个人合计、单位合计和应收合计。

2026 年深圳口径：

- 个人养老 = 社保基数 × 8%。
- 单位养老 = 社保基数 × 16%。
- 医疗和生育计算基数 = max（员工社保基数，6727）。
- 个人医疗 = 医疗和生育计算基数 × 2%。
- 单位医疗 = 医疗和生育计算基数 × 6%。
- 单位生育 = 医疗和生育计算基数 × 0.5%。
- 单位工伤 = 社保基数 × 0.8%。
- 个人失业 = 社保基数 × 0.2%。
- 单位失业 = 社保基数 × 0.8%。
- 深户地方补充养老 = 社保基数 × 1%；非深户为 0。
- 每个单项独立四舍五入到分，再计算个人、单位和应收合计。

匹配成功必须同时满足：

1. Excel人员能唯一关联员工；
2. Excel缴费工资与员工档案社保基数一致；
3. 所属公司一致；
4. 户口信息有效；
5. 每个险种金额与后台复算结果一致；
6. Excel内部个人、单位、应收合计正确；
7. 后台复算合计与Excel合计一致。

金额按分精确比较，差 0.01 元即进入待确认。不得再通过分别套用深户和非深户公式后选择更接近 Excel 的结果。

金额匹配率 = 自动完全匹配人数 ÷ Excel有效明细总人数。无法关联、基础资料缺失和金额不一致均计入分母并降低匹配率。人工确认差异不会倒算为自动匹配。

## 对抗性审查基线

对 `202607示例企业社保缴费明细.xlsx` 的独立复算结果：

- Excel有效明细 68 人，68 人均可通过身份证或唯一姓名关联员工。
- 68 人员工档案社保基数均与 Excel 缴费工资一致。
- 严格映射户籍后，47 人自动完全匹配。
- 18 人员工档案户口信息为空，应进入待确认。
- 演示员工207、演示员工221、演示员工172的员工档案为非深圳户籍，但 Excel 存在 1% 地方补充养老，应进入待确认。
- 严格自动匹配率为 47/68，即 69.12%，不能显示为 100%。

## 社保页面结构与操作

页面从上到下保持四区：

1. 社保汇总看板；
2. Excel上传与批次管理；
3. 待确认社保信息明细；
4. 社保信息明细。

看板支持期间和所属公司筛选，展示Excel人数、个人合计、单位合计、应收合计、严格金额匹配率、自动关联率、待确认人数，并在全部公司视图展示示例总部和示例研发中心汇总。

上传时自动根据身份证和姓名关联员工及所属公司，不要求用户预选公司。同一期间、同一文件哈希禁止重复上传；同一期间存在未完成批次时给出明确提示。

每个待确认行显示：员工、所属公司、档案社保基数、Excel缴费工资、系统户籍判断、各险种档案复算值、Excel值、差额、自动原因、备注和操作。

待确认行提供：

- “确认并纳入本批次”：必须选择有效员工并填写备注；保留原差异和确认人、确认时间。
- “忽略此行”：必须填写原因；该行不进入正式明细，但保留在批次审计记录。

批次列表每行直接提供：

- “确认导入”：仅当所有待确认行都已确认或忽略后可用；整批原子化转为正式明细。
- “取消批次”：取消本次解析结果，不影响既有正式批次和历史数据。

确认新批次后，同期间旧的当前批次转为历史批次，不覆盖或删除历史记录。正式明细只展示当前批次中自动匹配或人工确认纳入的行。

## 数据与迁移

- 现有户口信息值按上述五项规范化；无法规范化的值保留原始内容并标记待完善，禁止静默猜测。
- 已上传但未确认的重复7月批次不自动删除；页面提供取消操作，由管理员明确处理。
- 社保政策参数按期间和公司隔离，深圳规则不能直接用于示例研发中心。
- 当前员工单值社保基数先作为现行基数使用；后续补充按生效年月保留基数历史时，不改变本次页面和对账接口边界。

## 错误处理与审计

- 缺社保基数、缺户口信息、公司不一致、人员无法关联、基数不一致、单项金额不一致、Excel内部合计错误分别生成明确原因。
- 任何待确认操作都记录原Excel值、后台复算值、操作人、时间、备注和最终处理状态。
- 导入确认与取消均在后端校验批次状态，前端按钮禁用不能代替后端校验。

## 验证

- 员工表：表头和第一列固定、20人分页、筛选与翻页组合、缺失字段提示、下拉选项保存。
- 计算：5000、6000、6727、10000等基数；深户与非深户；医疗下限；逐项四舍五入。
- 对账：基数不一致、户籍缺失、地方补充养老冲突、金额差0.01、员工无法关联、重复员工、Excel合计错误。
- 批次：确认、忽略、整批生效、取消、重复上传、同期间历史保留。
- 回归：2026年7月原表严格结果为47人自动匹配、21人待确认、匹配率69.12%。
