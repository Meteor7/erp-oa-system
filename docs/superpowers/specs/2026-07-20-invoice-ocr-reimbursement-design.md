# 发票 OCR 与费用付款/报销单集成设计

日期：2026-07-20
状态：用户已确认功能设计，待书面规格复核

## 1. 目标与范围

在现有“新增费用付款/报销单”中直接增加批量发票上传和本地 OCR。支持 PDF、JPG、JPEG、PNG，识别后允许人工修改并确认七项：发票类别、项目名称、开票日期、发票号码、税前金额、税额、合计金额。

发票类别保留票面完整原文，例如“电子发票（普通发票）”；项目名称有多项时完整保留并用“；”分隔；未识别到的字段保持空白，不猜测、不从文件名补值。本期不验证真伪，不调用外部 OCR、税务或第三方接口。

完成标准是现有平台链接可实际上传样本、运行本地 OCR、显示和修改七项、确认、查重，并在每条费用明细后查看正确的原发票。

## 2. 当前审查结论

- 当前报销单只有基本信息、费用明细和付款信息，没有七项发票字段。
- 当前“费用项目”是公司内部报销分类，不等于票面“项目名称”，不能相互覆盖。
- 当前 `OA Invoice Attachment` 仅存文件基本信息和状态，没有 OCR 七项、哈希、确认记录。
- 当前消费明细只支持单文件上传，没有批量 OCR。
- 当前部分 OA API 使用 `ignore_permissions=True`；本功能必须增加服务端所有权和角色校验，不能信任客户端传入的确认或查重状态。
- 当前 Windows 工作区和运行中 Frappe 均有既有改动。开发必须使用独立功能分支和隔离环境，测试通过前不修改运行中数据。

## 3. 选定方案

### 3.1 界面内嵌，后台独立

在“基本信息”和“费用明细”之间增加“发票识别明细”。一张发票一行，显示文件、七项字段、关联费用明细、状态、查重结果和操作。

后台使用独立发票批次与发票记录，不在单据头只放一组七字段，也不把票面字段混入费用明细。原因是单据头无法表达多张发票，费用行也无法自然表达一条费用关联多张发票。

### 3.2 费用明细关联

- 一条费用明细可关联多张发票。
- 一张发票只能关联一条费用明细，且不能用于两张有效报销单。
- 每条费用明细增加稳定 `line_key`，关联不依赖表格行号，重排后不能串票。
- 删除已关联发票的明细前必须重新关联或解除关联，不得连带删除发票文件。
- 草稿阶段可调整；提交审批后锁定，普通用户不能替换、删除或重新关联。

## 4. 用户流程

1. 用户打开“新增费用付款/报销单”，每批最多上传 20 个文件，每个不超过 10 MB。
2. 文件存为 Frappe 私有附件，服务端校验扩展名、MIME/文件签名、大小并计算 SHA-256。
3. 完全相同文件先被识别；其余文件进入本地 OCR 队列，状态为“排队中”“识别中”。
4. OCR 返回七项候选值和字段提示；缺失项留空。
5. 用户修改后点击“确认”。系统同时保存 OCR 原值、人工确认值、确认人和时间。
6. 用户将发票关联到费用明细。系统可按“发票类别＋项目名称”推荐内部费用项目，但不得自动覆盖用户选择。
7. 保存草稿允许 OCR 尚在处理；提交审批时：
   - 有发票则所有纳入报销的发票必须已确认，且没有未处理重复或识别失败；
   - 没有发票允许提交，但必须填写无票原因。
8. 报销单详情和审批页的每条费用明细末尾显示“查看发票（N）”，点击打开私有预览抽屉。

未保存表单的上传批次归当前用户保留 7 天，可恢复。仅自动清理超过 7 天、未确认且未关联的孤立文件；确认或关联文件绝不自动删除。

## 5. 界面和金额规则

“发票识别明细”每行包含：文件预览、七项可编辑字段、关联费用明细、识别/确认状态、查重提示、重试、确认和移除操作。桌面端允许横向滚动，低置信度或缺失字段高亮，但结果必须人工确认。

费用明细末尾增加“发票”列：无关联显示“未关联”，有关联显示“查看发票（N）”。预览抽屉展示原文件、七项确认值、状态、查重结果和关联信息，并沿用水印及查看日志。

金额使用两位小数 Decimal/Currency。若“税前金额＋税额”与“合计金额”相差超过 0.02 元，提示人工复核，不自动更正。费用明细金额与关联发票合计不一致时提示；允许部分报销，但提交时要求填写差异说明。报销单总额仍取费用明细合计。

## 6. 数据模型

### `OA Invoice Import Batch`

保存一次批量上传：创建人、状态、临时表单令牌、关联报销单、各状态数量、创建及过期时间。用于未保存表单的异步处理和恢复。

### `OA Invoice Record`

每张发票一条独立记录：批次、私有 File、原文件名、MIME、大小、SHA-256、七项确认值、OCR 原始文本与结构化原值、字段提示、状态、重复命中及原因、关联报销单、费用明细 `line_key`、上传人、确认人/时间、失败原因和重试次数。

状态使用“排队中、识别中、待确认、已确认、疑似重复、失败、已排除”，不再使用会暗示真伪验真的“已验证”。发票号码必须按文本保存，避免前导零或长号码精度丢失；人工修改不得覆盖原始 OCR 值。

### 现有结构最小扩展

- `OA Approval Expense Line` 增加稳定 `line_key`，并维护发票数量和汇总状态。
- `OA Approval Request` 增加发票批次/汇总关联，不复制七项到单据头。
- 保留 `OA Consumption Detail` 和旧 `OA Invoice Attachment`，不删除旧数据、不破坏消费明细下推；详情页兼容展示新旧附件。

## 7. 本地 OCR 部署

新增 PaddleOCR sidecar 容器：只加入 Docker 内部网络，不发布主机端口。Frappe 后台任务读取私有文件后通过容器内网调用。sidecar 只负责 PDF/图像预处理、OCR 和字段候选提取；权限、查重、确认及报销关联全部由 Frappe 管理。

固定 PaddleOCR、PaddlePaddle 和系统依赖版本；模型放在 Docker 命名卷，提供健康检查、超时和资源限制。OCR 不可用时，现有 OA 页面和草稿保存仍可用，只阻止未完成发票提交审批。原 PDF 和图片不被替换或改写，内容不发送到外部服务。

## 8. 查重、权限和失败处理

查重分两层：

1. SHA-256 完全一致：直接标记重复。
2. OCR 后以“发票号码＋开票日期＋合计金额”比对已确认记录：标记疑似重复并阻止普通提交。

为避免旧式短号码误判，财务角色可对照两份原票并填写原因后解除疑似重复；系统记录操作者、时间和原因。前端不能直接设置查重或确认状态。

文件始终私有；预览接口每次验证用户是否有权查看所属报销单。新增写接口校验记录所有者、当前状态和角色。单个文件失败不终止整个批次；损坏文件、密码 PDF、不支持格式、超时或 OCR 服务不可用均显示明确原因并允许重试或排除。保存请求与关联发票在同一数据库事务内完成，避免半关联状态。

## 9. 代码边界

为避免继续扩大当前较大的 `ExpenseWorkbench.vue`，拆分为：

- 发票识别面板组件：批量上传、状态和七字段编辑；
- 发票预览抽屉组件：私有预览和确认值；
- 前端发票 API/状态模块；
- Frappe 发票服务：权限、批次、状态机、查重和关联；
- OCR 适配器：调用本地 sidecar，可在测试中替换；
- OCR sidecar：文件识别与候选字段提取。

不进行与发票功能无关的重构。

## 10. 测试与验收

自动测试覆盖：七字段解析、缺失留空、标题原文、多项目名称、金额精度、两层查重、财务解除、一明细多发票、一发票单一关联、明细重排/删除保护、提交校验、无票原因、权限、新旧附件兼容，以及 OCR 不可用时的降级。

使用用户提供的 15 张样本隔离验收：全部进入批次并产生明确结果或明确失败原因；字段级准确率不低于现有 POC 约 95%；文件名不参与字段生成；重复能被识别；逐行预览不串票。

平台最终验收：打开现有链接，批量上传样本，查看/修改并确认七项，关联费用明细，保存草稿，验证重复拦截，提交测试单，并在审批详情逐行查看正确原票；同时验证原有 OA、消费明细下推和其他页面未受破坏。

## 11. 部署与回滚

1. 全部开发位于 `feat/invoice-ocr-reimbursement`，不提交到 `main`。
2. 先在隔离测试站点和 OCR 容器验证，不连接正式业务数据。
3. 部署前备份数据库、私有文件和应用版本。
4. 先启动 sidecar 并通过健康检查，再迁移新增 DocType、构建前端并执行平台冒烟测试。
5. 通过后才在现有平台开放使用。

回滚时停止 sidecar 并切回原应用版本。结构变化全部为加法，不删除旧 DocType 或旧字段；回滚不会自动删除发票和业务记录，只按保留规则清理明确的孤立批次。
