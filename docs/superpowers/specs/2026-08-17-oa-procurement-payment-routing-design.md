# OA 采购付款分流与京东会签修复设计

日期：2026-08-17

## 目标

让 Docker 中的 OA 审批严格遵循《审批中心四类审批流程图-修订版-2026-08-12》和用户后续 23 条确认意见。本次只修复采购付款主链和京东购买会签；金蝶、同供应商自动合并、人工异常审批人员和自动催办/定制化看板继续挂起。

## 已确认业务设计

### 采购付款阶段

付款阶段不再由申请人自由决定，而由结构化付款计划和来源采购的履约状态决定：

- 到货前付款比例大于 0：预付款。
- 到货前付款比例为 100：仍属于 100%预付款，不使用“全额付款”绕开预付款规则。
- 没有预付款：不生成到货前付款审批，等待到货和验收。
- 已完成到货、验收且尚有应付金额：到货款或尾款。
- 到货后一次支付全部金额：到货后全额付款，与到货前 100%预付款明确区分。

### 审批路线

- 预付款：演示员工21审批 → 演示员工29审批 → 财务办理付款。
- 到货款、尾款、到货后全额付款：资料与状态校验 → 财务付款条件审核（演示员工13） → 演示员工21审批 → 演示员工29审批 → 财务办理付款（演示员工13）。
- 财务付款是 handle 办理节点，不是 approve 审批节点，页面必须分别显示“审批”和“办理”。

### 前置门槛

- 预付款：来源采购申请已完成，供应商存在，演示员工116或 PO、付款计划已归档；100%预付款还必须有预计到货日期和风险说明。
- 到货后付款：来源采购必须全部到货或关闭未交数量、验收通过，并归档验收资料和发票。
- “全额付款”旧值不得继续作为无条件付款入口；新提交必须明确为 100%预付款或到货后全额付款。
- 发票金额、付款计划金额、审批金额和重复发票的自动核验另有既有能力时复用；本次至少保证发票和验收资料为服务端硬门槛。

### 京东购买会签

京东购买生成一个 mode=all 的并行会签节点，审批人为“人事经理”和演示员工21。两人同时收到待办，两人全部通过后节点才完成；任一人可定向驳回。其他购买仍只走直属上级。

### 看板与催办

本次保证付款阶段、业务状态和当前节点准确，为后续看板提供可靠数据。下一阶段再实现角色定制看板、预付款逾期自动提醒、到货催办和异常升级，不在本次混入定时任务。

## 兼容与数据处理

- 保留已有到货、验收、退换货、预付款核销和关闭状态。
- 删除本轮旧流程测试批次的采购付款数据，重新创建能覆盖预付款、尾款和到货后全额付款的审批中心测试数据。
- 已有正式业务数据不做批量迁移；遇到旧“全额付款”记录只读保留，新提交禁止继续使用旧语义。

## 验收

1. 预付款没有财务条件审核节点。
2. 到货款、尾款和到货后全额付款具有财务条件审核节点。
3. 未到货、未验收、缺验收资料或缺发票时无法提交到货后付款。
4. 100%到货前付款按预付款处理。
5. 京东购买同时给人事经理和演示员工21待办，两人均通过才流转。
6. 页面区分审批节点和财务办理节点。
7. 后端测试、前端测试、前端构建和 Docker 页面验证全部通过。
